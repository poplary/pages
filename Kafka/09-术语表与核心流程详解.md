# Kafka 关键术语与核心流程详解

> 本文是全部 8 个主题文件的术语索引与流程参考。遇到不熟悉的术语或想理解某流程的完整链路时，查阅本文件。

---

## 一、关键术语速查表

### 副本与分区

| 术语 | 全称 | 含义 |
|------|------|------|
| **Partition** | 分区 | 主题的水平切分单元，是并行度和有序性的边界。单分区内消息有序，跨分区不保证。 |
| **Replica** | 副本 | 分区的数据拷贝，分布在多个 Broker 上实现容错。 |
| **Leader** | 领导副本 | 每个分区有一个 Leader 副本，处理所有读写请求。 |
| **Follower** | 跟随者副本 | 从 Leader 异步拉取数据做同步，不处理客户端读写（KIP-392 例外）。 |
| **ISR** | In-Sync Replicas | 与 Leader 保持同步的副本集合，只有 ISR 中的副本能被选为 Leader。 |
| **OSR** | Out-of-Sync Replicas | 落后于 Leader 的副本集合（不在 ISR 中）。 |
| **AR** | Assigned Replicas | 分区的全部分配副本，AR = ISR + OSR。 |
| **RF** | Replication Factor | 副本因子，每个分区的副本总数，生产建议 ≥3。 |
| **MIR** | min.insync.replicas | 最小同步副本数，acks=all 时需满足的最小写入确认数，建议 ≥2。 |
| **Preferred Replica** | 优先副本 | 副本列表中的第一个副本，优先选为 Leader 以均衡负载。 |

### 位移与水位

| 术语 | 全称 | 含义 |
|------|------|------|
| **Offset** | 位移 | 分区内消息的唯一编号，单调递增，消费者用位移标记消费进度。 |
| **LEO** | Log End Offset | 每个副本的最后一条消息的位移 +1（即下一条待写入位置）。 |
| **HW** | High Watermark | 高水位 = 所有 ISR 副本 LEO 的最小值。HW 以下消息对消费者可见（已提交）。不变式：HW ≤ LEO。 |
| **LSO** | Last Stable Offset | 事务模式下最早未完成事务的位移。LSO ≤ HW，read_committed 消费者只能读 LSO 以下。 |
| **Leader Epoch** | 领导者纪元 | 每次 Leader 切换递增的纪元号（KIP-101，0.11 引入），存于 `leader-epoch-checkpoint` 文件，防止基于错乱 HW 截断丢数据。 |
| **Committed Offset** | 已提交位移 | 消费者成功提交到 `__consumer_offsets` 的位移，标记消费进度。 |

### 消费者组与重平衡

| 术语 | 全称 | 含义 |
|------|------|------|
| **Consumer Group** | 消费者组 | 一组协同消费的消费者实例，组内每分区仅一个实例消费。一机制实现 P2P（同组）与 Pub/Sub（不同组）。 |
| **Coordinator** | 组协调器 | 负责管理消费者组成员、触发重平衡、管理位移提交的 Broker。通过 `abs(groupId.hashCode % 50)` 定位。 |
| **Rebalance** | 重平衡 | 消费者组成员变更时重新分配分区的过程。三代演进：经典（STW）→ 增量协作（KIP-480）→ 新协议（KIP-848）。 |
| **Assignor** | 分配策略 | 决定分区如何分配给消费者的算法：Range / RoundRobin / Sticky / CooperativeSticky。 |
| **Heartbeat** | 心跳 | 消费者周期性发给 Coordinator 的保活信号，间隔 `heartbeat.interval.ms`。 |
| **Session Timeout** | 会话超时 | `session.timeout.ms`，超时未收心跳则成员被踢出，触发重平衡。 |
| **Poll Timeout** | 轮询超时 | `max.poll.interval.ms`，两次 poll 最大间隔，超时判定消费者处理卡死，触发重平衡。 |

### 生产者与事务

| 术语 | 全称 | 含义 |
|------|------|------|
| **PID** | Producer ID | Broker 为每个生产者会话分配的唯一 ID，幂等性的基础。 |
| **Epoch** | 纪元 | 事务生产者每次重启递增的纪元号，防止「僵尸生产者」并行写。 |
| **Sequence Number** | 序列号 | 每分区递增的序号，Broker 据此去重（幂等机制）。约束：`max.in.flight ≤ 5`。 |
| **EOS** | Exactly-Once Semantics | 精确一次语义 = 幂等 Producer + 事务 + 消费端幂等。 |
| **TC** | Transaction Coordinator | 事务协调器，管理事务状态机，写入 `__transaction_state` 内部主题。 |
| **read_committed** | 读已提交 | 消费者隔离级别，只读已提交事务的消息（跳过 abort 的）。 |

### 集群与元数据

| 术语 | 全称 | 含义 |
|------|------|------|
| **Broker** | 代理 | Kafka 集群中的一个服务节点，处理读写请求。 |
| **Controller** | 控制器 | 集群中负责 Leader 选举、分区分配、Broker 上下线的特殊 Broker（KRaft 下为独立 Controller 节点）。 |
| **KRaft** | Kafka Raft Mode | Kafka 自带的 Raft 共识元数据管理模式，4.0 起为唯一模式（移除 ZooKeeper）。 |
| **Quorum** | 仲裁 | KRaft 中奇数个 Controller 节点组成的共识组，多数派（N/2+1）可写入。 |
| **Active Controller** | 活跃控制器 | Quorum 中通过 Raft 选出的 Leader，处理所有元数据写请求。 |

### 内部主题

| 主题名 | 含义 |
|--------|------|
| `__consumer_offsets` | 消费者位移主题，50 分区，存位移提交。key=`<group,topic,partition>`。 |
| `__transaction_state` | 事务状态主题，50 分区，存事务状态日志。每个 transactional.id 映射到一个分区。 |
| `__cluster_metadata` | KRaft 元数据主题，单分区，存集群全部元数据（Broker/Topic/Partition/ACL/配置）。 |

## 二、核心流程详解

### 流程 1：生产者发送消息

```text
KafkaProducer.send() 完整链路:

1. 拦截器链 (ProducerInterceptors.onSend)
   → 消息预处理/审计/统计

2. 序列化 (Serializer)
   → key/value → byte[]

3. 分区 (Partitioner / Balancer)
   → key != null: hash(key) % partitionCount
   → key == null: Sticky/LeastBytes (凑批发送)

4. 追加到 RecordAccumulator
   → 每分区一个 Deque<ProducerBatch>
   → 批次满(batch.size)或超时(linger.ms)触发发送
   → buffer.memory 满时阻塞(max.block.ms)

5. Sender 线程发送
   → 拉取就绪批次 → 按 Broker 分组
   → 构造 ProduceRequest → 网络发送

6. Broker 处理
   → Acceptor → Processor → RequestQueue → Handler
   → Log.append(): 追加到活跃段 → 更新 LEO
   → Follower 拉取同步 → 更新 HW
   → 返回 ProduceResponse

7. 处理响应
   → 成功: 执行回调
   → 失败: 重试(retries次) → 回调异常
```

### 流程 2：消费者拉取消息

```text
Consumer.poll() 完整链路:

1. 初始化(首次)
   → FindCoordinator: 找到 group 的 Coordinator Broker
     (abs(groupId.hashCode % 50) → 位移主题分区Leader)
   → 连接 Coordinator

2. 加入组(JoinGroup/SyncGroup)
   → JoinGroup → Coordinator 等待所有成员
   → 选 Leader → Leader 计算 Assignor 分配
   → SyncGroup → 各成员获自己的分区分配

3. 拉取循环
   → 构造 FetchRequest(分区 + 当前位移)
   → 发送到各分区 Leader Broker
   → Broker 返回消息(或阻塞 fetch.max.wait.ms)
   → 反序列化 → 调用用户处理逻辑

4. 心跳保活(独立线程)
   → 每 heartbeat.interval.ms 发心跳
   → 超时(session.timeout.ms) → 被踢 → 重平衡

5. 位移提交
   → 自动: 每 auto.commit.interval.ms 后台提交
   → 手动: commitSync()/commitAsync()
   → 写入 __consumer_offsets 主题
```

### 流程 3：消费者组重平衡（经典协议）

```text
触发条件:
  - 成员数变更(加入/离开/崩溃)
  - 订阅主题数变更
  - 主题分区数变更

经典协议流程(STOP-THE-WORLD):

1. 发现变更 → Coordinator 标记 RebalanceNeeded
   → 心跳响应中通知所有成员

2. 所有 Consumer 进入 Joining 状态 → 暂停消费(STW)

3. JoinGroup 阶段
   → 各 Consumer 发 JoinGroup(含订阅信息)
   → Coordinator 等待全部成员 Join
   → 选 Leader(第一个 Join 的 Consumer) ← 注意:不是选Coordinator

4. Leader 计算分配
   → Leader 用 Assignor 算法计算全量分区分配

5. SyncGroup 阶段(两轮)
   → Round1: Leader 发 SyncGroup(带全量分配方案)
   → Round2: 所有成员发 SyncGroup
   → Coordinator 校验一致性

6. 恢复消费
   → 各 Consumer 获自己的分配 → 恢复 poll

⚠️ 痛点: 步骤2-5 全程 STW, 大组可达数分钟
```

### 流程 4：KIP-848 新协议重平衡

```text
新协议流程(服务端驱动, 无STW):

1. 成员变更感知
   → 新成员加入/旧成员离开 → 通知 Coordinator

2. 服务端增量计算
   → Coordinator 内部计算增量分配
   → 仅变化部分重分配, 不变部分保持

3. 增量推送
   → Coordinator 通过心跳响应下发撤销/分配指令
   → 变化成员接收新分配
   → 不变成员继续消费(无感知)

4. 恢复消费
   → 变化成员完成重新分配后恢复
   → 近无停机

关键差异:
  经典: 客户端选Leader → Leader计算 → 两轮SyncGroup → STW
  新协议: 服务端Coordinator直接计算 → 增量推送 → 无STW
```

### 流程 5：副本同步与 HW 推进

```text
初始状态:
  Leader:  LEO=5  (offset 0-4 已写)
  Follower1: LEO=4  (落后1条)
  Follower2: LEO=3  (落后2条)
  HW = min(5,4,3) = 3 → offset 0-2 对消费者可见

第1轮同步:
  Follower1 发 FetchRequest(LEO=4) → 拉取 offset 4
  Follower1 写入 → LEO=5
  Follower2 发 FetchRequest(LEO=3) → 拉取 offset 3,4
  Follower2 写入 → LEO=5
  Leader 更新: HW = min(5,5,5) = 5 → offset 0-4 可见

⚠️ Follower 的 HW 延迟一个轮次:
  Follower 从 Leader 的 FetchResponse 中获取 Leader HW
  → 下一轮拉取时才更新本地 HW
  → 所以 Follower HW 总比 Leader HW 落后一轮

截断机制(Leader Epoch):
  新 Leader 上任 → 查 Follower 的 leader-epoch-checkpoint
  → 按各 Follower 该 epoch 的 LEO 截断
  → 防止基于错乱 HW 截断丢数据
```

### 流程 6：Leader 选举

```text
触发: 当前 Leader 所在 Broker 宕机

1. Controller 感知 Broker 宕机
   → KRaft: 心跳超时感知
   → ZK(旧): Watch 临时节点消失

2. 遍历该 Broker 上的所有分区
   → 对每个分区执行选举

3. 选举策略(按优先级):
   a. 优先副本选举: 副本列表第一个, 若在 ISR
   b. ISR 选举: 从 ISR 中选 LEO 最大的副本
   c. Unclean 选举(unclean.leader.election.enable=true):
      从 OSR 中选(可能丢数据, 生产建议false)
   d. ELR(KIP-966, 4.0预览): 比ISR更严格, 保证数据完整到HW

4. Controller 发送 LeaderAndIsrRequest
   → 新 Leader 开始服务
   → 更新元数据 → 通知所有 Broker

⚠️ 4.0 KRaft: Controller 选举改为 Raft 仲裁
   → 秒级选出新 Active Controller(旧 ZK 分钟级)
```

### 流程 7：KRaft 元数据传播

```text
元数据写入与传播:

1. 元数据变更请求
   → 创建Topic/分区变更/Broker上下线/ACL/配置
   → 发送到 Active Controller

2. Active Controller 写入元数据日志
   → 追加到 __cluster_metadata 主题(本地)
   → 记录类型: RegisterBrokerRecord / TopicRecord / ...

3. Raft 复制
   → 并行复制到所有 Controller Voter
   → 多数派(N/2+1)确认 → 提交(committed)

4. 元数据同步到 Broker
   → 所有 Broker 订阅 __cluster_metadata
   → 本地消费日志 → 更新元数据缓存
   → 延迟: 毫秒级(ZK 时代秒级)

5. 快照机制
   → 日志达阈值 → 生成快照
   → 新节点从快照 + 增量日志恢复(加速启动)

KIP-996 Pre-Vote(4.0):
   → 选举前先探查能否获多数票
   → 减少网络分区时的不必要选举
```

## 三、易混淆术语辨析

### Compaction vs Compression

```text
Compaction (压实/压实清理):
  → 同 Key 多条消息, 只保留最新版本
  → 用于 __consumer_offsets 等状态主题
  → log.cleanup.policy=compact

Compression (压缩):
  → 用算法减小消息体积(gzip/snappy/lz4/zstd)
  → compression.type 配置
  → Producer 压缩, Consumer 解压

两者独立, 可同时使用。
```

### at most once / at least once / exactly once

```text
at most once:  可能丢消息, 不重复
  → acks=0, 禁重试
  → 适合: 可丢的日志/监控数据

at least once: 不丢消息, 可能重复
  → acks=all + 重试(默认)
  → 适合: 一般业务(消费端幂等兜底)

exactly once:  不丢不重复
  → 幂等Producer(单分区单会话) + 事务(跨分区跨会话)
  → 4.0: enable.idempotence 默认true
  → 适合: 金融/支付(严格不重复)
```

### CommitSync vs CommitAsync

```text
commitSync():
  → 同步提交, 阻塞直到 Broker 确认
  → 自动重试, 可靠但影响 TPS
  → 适合: 关闭前保底、关键位移

commitAsync():
  → 异步提交, 不阻塞, 回调通知
  → 不重试(位移可能已过期)
  → 适合: 高频提交、平时消费

最佳实践:
  → 平时 commitAsync(不阻塞)
  → 关闭前 commitSync(保底)
```

### HW vs Leader Epoch 截断

```text
HW 截断(旧机制, 有丢数据风险):
  新 Leader 基于 HW 截断 Follower 日志
  → 问题: HW 可能错乱(网络分区脑裂)
  → 基于错 HW 截断 → 丢已提交消息

Leader Epoch 截断(0.11+, KIP-101):
  新 Leader 查 leader-epoch-checkpoint
  → 按各 epoch 对应的 LEO 截断
  → 不依赖 HW → 防止丢数据
  → 4.0 标准机制
```

### Sticky Partitioner vs Sticky Assignor

```text
Sticky Partitioner (生产者端, KIP-79):
  → 无 Key 时, 一批消息绑定同一分区
  → 凑大 batch → 批量发送更高效
  → 2.4 引入

Sticky Assignor (消费者端):
  → 重平衡时尽量保持原分配
  → 减少分区迁移
  → CooperativeStickyAssignor(KIP-480) 增量版

两者名字相似但作用端不同!
```
