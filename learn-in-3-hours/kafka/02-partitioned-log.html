02分区日志

Kafka 的根抽象：一条只能往后追加的账本

① 钩子

消息被“消费”之后就消失了吗？——不。它还静静地躺在硬盘上，可能躺 7 天。这正是 Kafka 区别于传统队列的根本：它是账本，不是取走就空的管道。

② 锚点

你见过 MySQL 的 binlog、Redis 的 AOF——都是“只追加、不改写”的日志。Kafka 把这个思想用到极致：一个主题（Topic）切成多个分区（Partition），每个分区就是一本 append-only 账本，消息按位移（Offset）从 0 单调递增编号。

技术细节

日志段（Log Segment）结构
每个分区在磁盘上是一个目录，内含多个 .log 段文件 + .index 偏移索引 + .timeindex 时间索引。active 段正在写入，写满（log.segment.bytes，默认 1GB）→ 滚动关闭，新开一个。查找消息：二分查找 .index 定位段内偏移 → 顺序扫描段内。所以 Kafka 的“随机读”实际是“段级二分 + 段内顺序”，开销极低。
Compact 清理策略
除默认 Delete（按时间/大小删除整个段）外，Compact 保留每个 key 的最新值，删旧值。过程：段分 clean/dirty 两半，clean 段保留，dirty 段重写只留最新 key。用途：__consumer_offsets（只留最新位移）、KRaft __cluster_metadata、change log 主题（Streams 状态快照）。
分区数上限
ZK 时代：单集群数万分区，元数据在 ZK 串行写入成为瓶颈。KRaft 时代：__cluster_metadata 用 Raft 复制，目标百万级分区。每个分区 = 一组日志段 + 一对 Leader/Follower，分区越多内存/文件句柄/网络连接越大——不是无限扩，是上限从数万提到百万。

③ 类比

分区日志 = 银行的多窗口排号账本：一个主题是一项业务（如“订单”），分区是不同的办理窗口，offset 是手里的号码牌。每个窗口的号从 0 开始单增，只能往后发新号，绝不回收改写旧号。

④ 边界

  • 账本会翻页丢弃：超过留存时间/大小，旧的日志段被整段删除（不是单条删）。
  • 排号是先到先得抢的，但“哪条消息进哪个窗口”由 key 哈希决定，不是时间序——所以跨分区无全局顺序，要全局有序只能单分区（牺牲并行）。
  • offset 是消息的位置编号（不可变），别和“消费者位移”（消费进度，可变）混为一谈——下页之后会反复出现。
