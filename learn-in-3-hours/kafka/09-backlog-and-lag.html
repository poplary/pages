09积压与 Lag

消费组越来越慢，Lag 一路涨——为什么越慢越追不上

① 钩子

半夜告警：某消费组 Lag 飙到 500 万。你扩了消费者，可 Lag 还在涨——因为消息已经掉出页缓存、落了盘，消费者在读磁盘，越读越慢。这就是“马太效应”。

② 锚点

第 03 页的页缓存、第 06 页的位移——这页把它们连成一个恶性循环。Lag 不是病，是症状；根因是“消费速度 < 生产速度”持续了一段时间。

技术细节

Lag 计算公式
Lag = LogEndOffset − ConsumerOffset。LogEndOffset：分区最新消息位移（HW 值），由 Broker 维护。ConsumerOffset：该消费者组在该分区的已提交位移。两个值都从 kafka-consumer-groups.sh --describe 或 Broker JMX 获取。
监控工具
① kafka-consumer-groups.sh --describe：命令行秒查。② Burrow（独立服务）：按 group/分区打分（GOOD/WARN/ERR），支持多集群。③ Prometheus + kafka_consumer_lag_metrics（JMX Exporter → Grafana）：生产标配。④ 4.0 新增 Consumer API 的 lag() 方法，应用内直接读。
各对策的具体调法
消费者少→扩消费者：但上限=分区数，超出的消费者闲置。处理慢→增大 fetch.min.bytes / max.poll.records 减少拉取频率；或优化业务逻辑（异步/批写）。入流量突增→临时扩分区（破坏 key 有序）；或上游限流（令牌桶）；或加消费者组（分流）。Broker 慢→检查磁盘 IO / 网络带宽 / GC。

③ 类比

还高利贷：欠得越多利息越高。Lag 就是欠的消息页数——欠得少时还在页缓存（内存，快），一旦掉出缓存落了盘（读磁盘，慢十倍），就还得更慢，欠得更多。滚到最后，老消息过了留存期被删——那才是真丢。

④ 边界

  • 扩消费者数超过分区数无效——多出的消费者闲着（分区是并行度上限）。
  • 增分区会破坏 key 顺序（hash(key)%分区数 变了），对依赖分区内有序的业务是灾难。
  • Lag=0 不代表业务处理成功——只是位移提交了，业务可能还没落库（先提交后处理的坑）。
  • 马太效应有救：只要消费速度重新超过生产速度，Lag 就会回落，消息重新进页缓存——关键别让它跨过“落盘”那道坎。
