01Kafka 是什么

它不只是一个消息队列，而是系统之间的缓冲带

① 钩子

双十一零点，订单系统每秒涌入 10 万单，后端数据库为什么没被当场打死？——中间一定有个东西，把洪峰接住、按下游的能力慢慢放水。

② 锚点

你用过 Redis 当高速字典、写过 HTTP 同步调用。可一旦遇到“上游瞬时洪峰 + 下游处理慢 + 还要跨系统解耦”，这三样都救不了你：Redis 是内存字典不是缓冲带，HTTP 同步调用会把慢的一端拖死整条链路。

技术细节

消息引擎：与 RabbitMQ / RocketMQ 的本质区别
Kafka 是日志模型（消费后数据不删，按留存期保留），RabbitMQ 是队列模型（消费后消息移除）。日志模型 → 可回放、多下游各读各、天然持久化。队列模型 → 取走即没、路由灵活、内存友好。选哪个取决于业务是否需要“回放”和“多下游独立消费”。
流处理平台：为什么 Streams 是库不是集群
Streams 嵌在你的应用 JAR 里，与业务代码同进程，无需独立运维一套集群。代价：无独立调度/弹性扩缩容——实例数 = 你部署的 JVM 个数，增减靠 K8s/运维，不是自动的。适合中小流量、拓扑简单的场景；大规模复杂窗口/状态仍推 Flink。
存储系统：与 MySQL/Redis 的定位差异
Kafka 不是 DB——不支持按 key 查询、没有索引、没有 ACID 事务跨表。但它能做“事件源”（Event Sourcing）：把状态变更事件存入 Kafka，任意时刻从 offset 0 重放 = 重建完整状态。配合 Compact 主题，每个 key 只留最新值，近似一张“可重放的 KV 表”。

③ 类比

Kafka 像小区的快递柜 + 蓄水池：上游随手把包裹塞进柜里就走（异步、不阻塞），下游按自己的节奏来取。关键差别——包裹取走后柜里还留着一份记录（账本），所以另一个小区也能来取一份。

④ 边界

  • 快递柜取走就空了；Kafka 的消息读后仍在（按留存保留，默认 7 天）——这是“账本”不是“队列”。
  • 蓄水池会溢出：磁盘写满、或留存时间到点，老消息会被删除，不是无限保留。
  • 消息是二进制字节，语义由你自己定——Kafka 不懂你的业务，只管搬运和留存。
