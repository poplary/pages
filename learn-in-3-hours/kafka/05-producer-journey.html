05生产者之旅

一条消息从 send() 到落盘，要过五道关；为什么有时会重复

① 钩子

调用 send(msg) 只要 1 毫秒就返回了，可 Kafka 偏偏可能再等 5 毫秒才真正发出去——它在等什么？等“凑一批发”。而重试时，同一条消息会不会发两遍？

② 锚点

你写过批量提交接口（攒一批再 INSERT）、用过带回执的快递。Kafka 生产者就是这二者的合体：分拣（分区）→ 攒车（凑批）→ 发运（Sender 线程）→ 回执（acks）→ 防重复签收（幂等）。

技术细节

分区路由算法
有 key：partition = hash(key) % numPartitions（默认 murmur2 哈希）。同 key 必同分区，分区内保序。无 key：StickyPartitioner（3.3+）同一批粘同一分区减少切换，下批再轮换；旧版纯 Round-Robin。自定义：实现 Partitioner 接口。
幂等 Producer 的 PID + seq 机制
enable.idempotence=true → Broker 返回 InitProducerId 请求时分配 PID（Producer ID，64bit）。每条消息带 (PID, 分区, seqNum)。Broker 每个 (PID, 分区) 维护一个 lastSeq：新 seq = lastSeq+1 → 接受；seq ≤ lastSeq → 重复丢弃；seq > lastSeq+1 → 乱序拒绝。PID 在生产者重启后重新分配，因此只保单会话。
事务 Producer（跨分区跨会话 exactly-once）
配 transactional.id → Broker 用它映射 PID + epoch。重启时 epoch+1 → 旧 PID 同 epoch 的请求被拒（防僵尸生产者）。流程：① InitProducerId（分配 PID+epoch）② BeginTxn ③ 发送 N 条消息到 N 个分区 ④ AddPartitionsToTxn ⑤ CommitTxn：写 commit 标记到事务日志（__transaction_state）→ 两阶段：先写 marker 到所有参与分区，再写 commit。消费端设 isolation.level=read_committed → 只读已提交消息。

③ 类比

邮局分拣：同一收件城市（key）的信总进同一个分拣格（分区），凑满一袋（batch.size）或等够时间（linger.ms）再装车发运，回执单回来才算寄达（acks）。怕快递员把同一封信投两次？给每封信编号，收件方按编号去重——这就是幂等。

④ 边界

  • linger.ms 的等待是“用延迟换吞吐”——追求低延迟就调小（甚至 0），追求吞吐就调大。
  • 幂等的边界：只保证单分区、单会话不重复。生产者重启后 PID 变了，旧 PID 重发的消息不会被新 PID 去重——跨会话/跨分区要事务 Producer（配 transactional.id，靠 epoch 防僵尸生产者）。
  • “同 key 同分区”保证分区内有序——但一旦增加分区数，hash(key)%分区数 的结果会变，原来的顺序就被打散。所以分区数最好一开始就定够，别轻易加。
