12生态一页通

一个日志层，长出整个生态——Connect 搬货，Streams 加工

① 钩子

学完核心四件套，Kafka 的故事就完了？不——“可回放的高吞吐账本”这层地基之上，长出了 Connect（搬运外部数据进出）和 Streams（就地做流式计算）。这两块是 Kafka 从“消息引擎”进化成“流处理平台”的拼图。

② 锚点

你已经掌握 Core（日志+副本+组）。Connect 和 Streams 都不是新引擎，而是建在 Core 之上的客户端：Connect 是标准化的搬运工，Streams 是随应用跑的计算库——都吃同一个日志层。

Streams vs Flink / Spark 定位

维度Kafka StreamsFlink / Spark Streaming
形态轻量客户端库（随应用进程）独立集群系统
部署零运维，嵌应用需独立集群调度
EOS原生（基于 Kafka 事务）需借助 Kafka 事务
适合中小流量、简单拓扑大规模、复杂窗口/状态

技术细节

Connect 运行模式
Standalone：单进程，适合小规模/测试，命令行 java -jar 直接跑。Distributed：多 Worker 组集群，REST API 管理 Connector，某 Worker 挂 → 其任务自动重分配到其他 Worker。任务（Task）是并行度单位，每个 Task 处理一部分分区——类似消费者组对分区的分配。
Streams 状态存储与容错
有状态操作（aggregate/count/join）→ 本地 RocksDB 状态存储 + changelog 主题（Compact）。容错：实例挂 → 新实例从 changelog 重建 RocksDB → 继续处理。RocksDB 在磁盘，changelog 在 Kafka——两层备份。无状态操作（filter/map）无需状态存储，实例挂了直接重启。
MirrorMaker 2（跨集群复制）
基于 Connect 框架的 Connector，自动检测源集群新主题并复制。配置：源→目标集群映射 + 复制因子 + 主题正则过滤。4.0 起 MM1 弃用，MM2 是唯一跨集群复制工具。用途：灾备、聚合、多区域。

③ 类比

Core 是发动机（账本+副本+组），Connect 是进货口/出货口（标准化码头，免手写搬运），Streams 是车载加工车间（随车跑、就地算，不是独立车队）。流表二元性就像：账本流水（流）和资产负债表（表）是同一笔生意的两种看法。

④ 边界

  • Streams 是库不是集群——没有独立调度/弹性部署，复杂拓扑和超大流量仍推 Flink。
  • Schema 管理（消息结构注册/演进）官方核心不带，是 Confluent 生态的 Schema Registry——用需额外部署。
  • 跨集群备份用 MirrorMaker 2（4.0 起 MM1 弃用），不是 Streams 的职责。
