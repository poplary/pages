03为什么这么快

机械盘跑出内存速的秘密：四板斧合起来省掉每一次“冤枉路”

① 钩子

机械硬盘随机写每秒只有几百次 IOPS，可 Kafka 单机却能扛住每秒几十万条消息——它凭什么把“最慢的磁盘”用出了“内存的感觉”？

② 锚点

MySQL 用 B+ 树把随机 IO 摊成顺序 IO，绕开盘片寻道。Kafka 走同一条物理规律，但更彻底：四板斧一起上。

技术细节

① 顺序写
append-only log → 磁头沿同一方向连续写入，无 seek/rotate 等待。机械盘：随机≈100 IOPS，顺序≈100 MB/s（千倍差距）。SSD：随机也快，但顺序写仍减少写放大（FTL 合并），批量仍省往返。
② 页缓存
Kafka 写入路径：FileChannel.write() → 数据进入 OS page cache → 返回成功。OS 的 pdflush/flusher 线程异步刷盘。Kafka 不调 fsync()——持久性靠副本机制（多 Broker），而非单机 fsync。读同理：数据若仍在 page cache 中，直接从内存返回，不经磁盘。
③ 零拷贝 sendfile
传统 read()+write()：磁盘→DMA 内核buf→CPU 用户buf→CPU socketbuf→DMA 网卡 = 4次拷贝(2DMA+2CPU) + 2次系统调用 + 2次上下文切换。sendfile()：磁盘→DMA 内核buf→SG-DMA 网卡 = 0次CPU拷贝 + 1次系统调用。scatter-gather DMA：内核只把(偏移+长度)描述符传给网卡，数据全程不进用户态。Java 入口：FileChannel.transferTo()。前提：数据不压缩、不格式转换——否则 Broker 需解压重压，零拷贝失效。
④ 攒批发送
生产端：batch.size=16KB（默认），linger.ms=0（默认）→ 调 linger.ms>0 才真正等凑满。批内压缩：compression.type=zstd/lz4/snappy/gzip，批越大压缩比越高。Broker：整批落盘（一次顺序写），整批复制给副本。消费端：整批拉取（fetch.min.bytes），批内消息不逐条解码。网络往返次数 × 批大小 = 单次往返吞吐。

③ 类比

搬砖：一块一块搬（随机写、逐条发）跑断腿；装满一车皮一次拉走（顺序写 + 攒批），一趟顶一百趟。零拷贝 = 砖直接从仓库甩到卡车上，不经过门卫手里登记。

④ 边界

  • SSD 随机写也快了，但顺序写 + 批量的优势依然成立——SSD 顺序写仍省写放大，批量仍省往返。
  • 零拷贝只在消费端读取成立（sendfile 把文件从内核直接甩到网卡）；生产端写入仍走页缓存。
  • 一旦发生消息格式转换（4.0 已移除 v0/v1 兼容），Broker 要解压重压，零拷贝当场失效、CPU 飙升——4.0 只保留 v2 正是为了消除此痛点。
💡 金句
顺序 + 批量，让机械盘跑出内存速
