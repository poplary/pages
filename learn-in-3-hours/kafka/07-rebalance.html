07重平衡

成员一变，分区重洗——三代协议如何从“全员停工”走到“近无停机”

① 钩子

一个消费者卡了 5 分钟，为什么整个组都跟着停下来等它？老版重平衡就是这种“一人请假、全班停课”的脾气。Kafka 花了三代协议才把它治好。

② 锚点

上一页的消费者组分工：谁领哪几个分区是“分配方案”。成员一增一减，方案就得重排——这就是重平衡（Rebalance）。

触发条件与关键参数

三种变化会触发重平衡：①成员数变（加入/离开/崩溃被踢，占 99%）②订阅主题数变（正则订阅新匹配）③分区数增（只能增不能减）。

参数默认作用
session.timeout.ms10s/45s心跳超时→被踢（误踢主因）
heartbeat.interval.ms3s心跳频率，建议 = session 的 1/3
max.poll.interval.ms5min两次 poll 最大间隔，超时判定卡死

技术细节

EAGER vs COOPERATIVE 重平衡策略
EAGER（旧协议）：全部消费者撤销所有分区 → 重新分配 → 全停全启，Stop-The-World。COOPERATIVE（KIP-429，渐进式）：只撤销需要移动的分区，未受影响的消费者不停。类似“渐进式搬家”——只搬要换的房间，不搬全楼。KIP-848 新消费组协议默认渐进式。
KIP-848 新消费组协议流程
旧协议：Consumer ↔ GroupCoordinator：FindCoordinator → JoinGroup → SyncGroup → Heartbeat。新协议：Consumer 直接向 Broker 声明目标分区（ConsumerAssignments），Broker 按声明分配——无需 JoinGroup/SyncGroup 两轮 RPC。重平衡时只通知受影响的消费者重新声明，未影响的无感。4.0 默认启用。
max.poll.interval.ms 的作用
两次 poll() 间隔超过此值（默认 5min）→ 消费者被踢出组 → 触发重平衡。所以 poll() 里的业务逻辑不能超过 5min——否则要么调大此值，要么把耗时操作移到 poll 之外（异步处理 + 手动提交）。

③ 类比

小组重新分工：老办法是有人请假就全班停下、开会重排所有人座位（经典 STW）；新办法是组长直接把离职者的活分给别人，其他人手不停（KIP-848 增量协同）。

④ 边界

  • 重平衡不能完全避免——成员增减必然要重排，只能减少“误伤”和停顿。
  • 类比在“新协议秒级”处不再准确：仍有极小的撤销/分配窗口，只是小到几乎无感。
  • 4.0 新协议服务端默认启用，但客户端要显式 group.protocol=consumer 才能享受；不开则走经典协议（向后兼容）。
