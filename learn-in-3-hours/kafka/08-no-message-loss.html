08不丢消息清单

Kafka 只保证“已提交”消息；丢消息从来不是 Kafka 丢的，是配置丢的

① 钩子

都说 Kafka 可靠，可你的消息还是丢了——查日志发现 send 成功了、消费也跑了，偏偏中间某条不见了。问题不在 Kafka，在三道防线只设了一道。

② 锚点

第 04 页的 acks/ISR，第 06 页的位移提交——这页把它们组成一张“不丢”配置清单。可靠性从来是配置出来的，不是天生的。

三种交付语义

语义表现配置用途
at most once可能丢、不重复acks=0 禁重试可丢的日志
at least once不丢、可能重复acks=all+重试（默认）一般业务（消费端幂等兜底）
exactly once不丢不重复幂等+事务+消费端幂等支付/金融

技术细节

生产者端：为什么 retries + idempotence 要一起配
retries 调大后，网络抖动会触发重发。无幂等 → 重发成功两次 → 重复。开幂等后 Broker 按 (PID, 分区, seq) 去重，重发自动被吞。4.0 默认 enable.idempotence=true，retries=Integer.MAX_VALUE。若不用幂等，retries 应配合 max.in.flight.requests.per.connection≤5 保证分区内有序。
Broker 端：min.insync.replicas 的具体效果
假设 RF=3, min.insync.replicas=2。正常时 ISR=3, acks=all 要 3 个确认。1 个 Follower 挂 → ISR=2, 仍能写入（2≥2）。2 个 Follower 全挂 → ISR=1 < 2 → NotEnoughReplicasException，拒绝写入。这就是“宁可不可用也不丢”。
消费者端：enable.auto.commit=false 后的三种提交策略
① 同步提交 commitSync()：阻塞等 Broker 确认，最安全但最慢。② 异步提交 commitAsync()：非阻塞，可能丢（处理后提交前:提交前崩溃→重启后重复处理）。③ 组合：commitAsync() + commitSync()（关闭前同步兜底）。Kafka 4.0 消费者默认异步自动提交，需手动关闭。
exactly-once 语义的真正条件
生产者事务 + 消费者 read_committed + 业务幂等 = 端到端 exactly-once。单靠 Kafka 事务只保“不重不漏”到日志，业务侧重复消费仍需幂等（如 DB 唯一键、Redis SETNX）。

③ 类比

寄贵重合同：寄件要回执（acks=all，所有分部签收才算）、收发室留三份底档（RF=3，且至少两份同步才算归档）、签收登记完才算送达（先验货再销单=先处理后提交）。三道手续，少一道就可能丢。

④ 边界

  • 这份清单买到的是“已提交消息不丢”——生产者发出但未应答的消息，Kafka 不保证（所以必须带回调重试）。
  • RF=MIR+1 是可用性与持久性的权衡：要更高持久性就提高 MIR，但要接受“可用副本更少”的代价。
  • exactly-once 有性能开销，且副作用操作（发短信）无法回滚——仍需业务幂等（唯一键去重 / outbox pattern）。
  • 极端情况：多数副本同时损坏，仍会丢。Kafka 买的是“单点故障不丢”，不是“末日不丢”。
💡 金句
不丢 = 三端都设防，缺一不可
