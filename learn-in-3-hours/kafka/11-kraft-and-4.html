11KRaft 与 Kafka 4.0

Kafka 自己就是个分布式系统——谁来管它自己

① 钩子

Kafka 管着别人家的分布式数据，可它自己也是个分布式系统——一群 Broker，谁当老大、谁记元数据？以前 Kafka 旁边总得站一个 ZooKeeper 当“秘书”，4.0 起 Kafka 把秘书炒了，自己管自己。

② 锚点

Redis Cluster 用 gossip 协调、MySQL 用主从——分布式系统总要个“管家”维护元数据（哪些主题、分区 Leader 在哪、谁上下线）。ZK 就是 Kafka 雇的外部管家；KRaft 是把管家职能收回 Kafka 自己。

技术细节

Raft 协议在 KRaft 中的角色
Raft 负责两件事：① Leader 选举（多数派投票选主，选举超时后发起）；② 元数据日志复制（Leader 写 → 多数 ISR 确认 → 提交）。与 Kafka 消息副本机制同构，但作用域不同：Raft 管 __cluster_metadata 主题（元数据：主题/分区/配置/ISR），消息数据的副本靠第 04 页的机制。
Controller 仲裁 vs 消息分区 Leader
Controller 仲裁 = 集群全局元数据的主节点（3 或 5 个 Controller 节点 Raft 仲裁）。消息分区 Leader = 每个分区各自的读写主（可分布在任意 Broker）。两者独立：Controller 节点挂不影响已有分区的读写（Leader 不变），只影响元数据变更（创建主题/重平衡等）。
ZK → KRaft 迁移路径
3.6+ 提供迁移工具：① 在 ZK 模式下运行迁移命令 → ② 工具把 ZK 元数据快照灌入 __cluster_metadata → ③ Broker 逐个重启为 KRaft 模式 → ④ 迁移完成后可移除 ZK。4.0 不再支持 ZK 模式，必须在 3.6–3.9 完成迁移后才能升级 4.0。

③ 类比

公司原来外聘秘书公司（ZK）管组织架构表，员工上下班、部门调整都找秘书登记；现在把组织架构表写进自家账本（__cluster_metadata 主题），谁来记账由多数投票（Raft）决定，所有员工订阅账本变更——一套系统全搞定。

④ 边界

  • Raft 多数派意味着 3 个 Controller 只能容忍挂 1 个（5 个容忍 2 个）——所以 Controller 节点要奇数个。
  • KRaft 管的是元数据（谁是谁、Leader 在哪），不管消息数据——消息数据仍靠副本机制（第 04 页）。
  • 4.0 是分水岭，但不能从 ZK 直跳 4.0：必须先在 3.6–3.9 完成迁移，再升 4.0。
  • KIP-848 新消费组协议（第 07 页）和 KIP-932 队列语义（第 10 页）是 4.0 的另外两大亮点，三者协同。
